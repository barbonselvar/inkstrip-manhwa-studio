## Owner setup, in order

1. Create a Supabase project in the appropriate region and configure backups/retention and billing limits. Keep the service-role key private. The application uses the official Supabase SSR and JavaScript libraries through same-origin server handlers; no Supabase session or service-role token is returned to browser JavaScript.
2. For a fresh target, apply `supabase/migrations/20261106101354_inkstrip_accounts.sql` followed by `supabase/migrations/20261106101958_harden_account_policy_helpers.sql` through the Supabase CLI migrations workflow or the SQL editor as the database owner. This migration is separate from the existing optional Neon/Grok scaffold and never runs against IndexedDB. It creates seven tables, a security-invoker project overview, ownership policies, service-only publication/rate/confirmation RPCs and a private `inkstrip-private` bucket. Both are already applied to the connected Inkstrip project; do not rerun them there. The second migration moves policy helpers into an unexposed schema, removes inherited browser-role grants and fixes search paths/indexes. Do not delete existing application data to rerun migrations.
3. Check **every** application table has RLS enabled. `anon` has no application-table access. `authenticated` can read only its verified user's profile and private project metadata; profile updates are column-limited. Cloud revisions/receipts can only be published by the server after ownership and integrity checks. Bucket visibility must remain private. Remove any unrelated permissive Storage policies that could grant access to this bucket: PostgreSQL permissive policies are OR-combined. Verify with two real test users, an unverified user and an anonymous client.
4. Enable email/password in Supabase Auth. **Enable Confirm email**, disable anonymous sign-ins for this application, and configure password policy to match the application: 12+ characters, upper/lowercase, number, symbol. Use breached-password protection if available in your plan; it is not required by the client. Set **email OTP length to six digits** and **OTP expiry to 600 seconds**. Configure provider resend/rate limits in addition to the durable application limits. Supabase controls random generation, hashing, invalidation, attempts and single use; Inkstrip does not store email OTPs. Verify latest-code invalidation and expiry in staging before enabling accounts.
5. For public production registration, configure a suitable SMTP provider in Supabase Auth with a verified sender and SPF/DKIM/DMARC. No paid provider is required by the application. For initial tests without a domain/provider, use the restricted built-in sender and link mode below; the owner selected this option. Its development limits are not a public production delivery guarantee. Store any future SMTP credentials only in the provider dashboard.
6. Choose the supported email mode. With custom SMTP, use `INKSTRIP_EMAIL_MODE=otp` (default), templates displaying `{{ .Token }}`, and six digits / 600 seconds. Suggested subjects: `Verify your Inkstrip account` and `Reset your Inkstrip password`. With Supabase's built-in sender for restricted initial tests, use `INKSTRIP_EMAIL_MODE=link` and leave its default templates intact: new Free projects cannot customize them without custom SMTP. Only authorized team recipients and the current two-messages/hour allowance are supported. No domain purchase or paid upgrade is needed for those tests. This is not a public production email service. Enable and test password-change security notifications where supported.

   Link mode requires `20261106134024_email_link_flows.sql` (already applied). It uses official SSR PKCE plus a hashed, expiring, single-use browser intent tied to the intended email. Recovery requires the provider's `PASSWORD_RECOVERY` event and an existing session-bound reset grant; a query parameter or ordinary signed-in session cannot authorize a reset. Open the latest link within ten minutes **in the same browser** that requested it. Requesting another link replaces that browser's intent. Do not paste links/tokens into chat or logs. Six-digit OTP mode remains available for a suitable future sender.

7. In Supabase Auth URL configuration, set Site URL to `https://inkstrip-manhwa-studio.vercel.app`. The app callback is `https://inkstrip-manhwa-studio.vercel.app/api/account/callback`. Add the narrow redirect allow-list pattern `https://inkstrip-manhwa-studio.vercel.app/api/account/callback?flow=*` to allow the random flow query value. Validate Supabase's current glob matcher in staging; if it requires a trailing glob after the callback path, use `https://inkstrip-manhwa-studio.vercel.app/api/account/callback**`, never an origin-wide production wildcard. The handler requires a matching HttpOnly flow cookie, consumes a single-use hashed flow record and exchanges the code through PKCE. It accepts no user-supplied return URL. Provider errors redirect only to a fixed account notice.
8. Google Cloud: create a Web application OAuth client, configure the consent screen, authorized production origin, scopes `openid`, `email`, `profile`, test users/publishing as required. Its **authorized redirect URI is Supabase's provider callback** `https://<project-ref>.supabase.co/auth/v1/callback` (use your actual Supabase/custom domain). Enter the client ID/secret in Supabase Auth → Google. These credentials never go into client code. Verify a confirmed email is returned.
9. Meta Developers: create an app supporting Facebook Login for web, configure app domains, production HTTPS site URL, privacy policy `/legal/privacy`, terms `/legal/terms`, valid OAuth redirect URI `https://<project-ref>.supabase.co/auth/v1/callback`, strict redirect matching, client OAuth and web OAuth. Request only required identity/email scopes; complete Meta review/live mode and its data deletion callback or instructions requirement. Account deletion instructions: `/account` → Security & account deletion → confirm identity → type DELETE. Put the app ID/secret in Supabase Auth → Facebook. Some Facebook identities do not supply a verified email: they cannot access protected features; use verified email login instead. Do not imply an unverified identity is sufficient.
10. Enable Supabase **manual identity linking** if Connect Google/Facebook is desired. Connections are initiated only from an authenticated verified account and checked against that same user ID after callback. Supabase may securely auto-link provider-verified identities under its own rules. Inkstrip never merges users by email. Test provider cancellations, identities sharing a verified email and wrong-account reauthentication in staging. Additional policy restrictions must be configured with Supabase if your organization disallows its automatic verified-identity linking.
11. Add the following **server-only** Vercel environment variables to the intended environment. Do not add `VITE_` or `NEXT_PUBLIC_` prefixes. Keep production credentials out of previews; use a separate staging Supabase project and canonical origin for staging. Configure variables through the owner dashboard/secret manager; no `.env` or secret values belong in Git.

## Security and operations

For link mode, add `https://inkstrip-manhwa-studio.vercel.app/api/account/email-callback?flow=*` in Supabase Authentication → URL Configuration. Keep Site URL at the exact production origin. Separately allow the actual test origin with the same fixed callback path for pre-release tests; never use an unrestricted host wildcard. The existing `/api/account/callback?flow=*` entry is for OAuth. Vercel Production has `INKSTRIP_EMAIL_MODE=link` prepared, but accounts remain disabled. This follow-up must not be deployed before the live release gates pass.

Supabase's advisor can report `auth_leaked_password_protection` on Free: the built-in check requires Pro or above. No billing change is authorized. Application strong-password and server rate-limit rules remain enabled. See [provider password security](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). This limitation does not replace mandatory live authorization checks.

Session cookies are HttpOnly, Secure on HTTPS, host-only and SameSite=Lax (OAuth compatible). CSRF cookies are HttpOnly/Strict; the matching in-memory token is issued by the no-store session endpoint, required with an exact Origin on every mutation. All private requests call provider `getUser`, check confirmed email and apply database/storage RLS. Remember session clamps cookies to 30 days; unchecked uses session cookies (browser session restoration settings can retain them). Provider JWT expiry/refresh/revocation remains authoritative. Immediate JWT revocation after global logout depends on Supabase's access-token lifetime; use a short provider JWT lifetime appropriate to your deployment.

Sensitive operations require a short, session-bound, single-use confirmation: current-password reauthentication or a new same-account OAuth code exchange. OAuth uses provider-supported prompts; provider SSO may reuse its existing session. This is not phishing-resistant MFA or an adaptive risk engine. Supabase's optional secure-password-change nonce policy may require additional provider UI; validate its behavior before enabling that policy. Inkstrip does not pretend to implement a risk engine or require email OTP on every login.

Recovery confirmation is a different grant from destructive-action reauthentication. Confirmations and OAuth intents store **only a hash of a cryptographically random nonce**, never an email code. SQL RPC updates consume them atomically. Rate limits use atomic PostgreSQL updates, not per-process counters. Authentication requests are capped by trusted deployment IP and hashed email subjects; deployment forwarded headers must remain managed by Vercel, not a public client-controlled reverse proxy. Provider-native rate limits remain required to cover direct provider API access.

Schedule service-owner cleanup of expired `inkstrip_rate_limits` and expired/consumed `inkstrip_account_actions`, and establish audit retention (for example 30 days according to your policy). Audit events contain event/outcome/request ID/optional user UUID and no secrets or artwork. Use Supabase's own Auth audit logs for provider events. Set storage quotas/monitoring at your provider: per-part upload limit is 2 MiB, a published package is at most 2 GB / 1,000 parts; all historical revisions are retained. Latest revision size is shown in the account area, not a claim about total billed storage. Interrupted upload chunks remain private and reusable; account deletion removes them too.

Account deletion marks the profile as deleting before cleanup so project and Storage reads immediately stop, removes owned files/receipts and finally deletes the Auth user with cascading database deletion. A timeout/failure leaves an explicit retry state, never reports success. Large accounts may need repeated fresh confirmations or operator cleanup within Vercel function limits. Local project copies are never removed. Do not remove the deleting marker to bypass failed cleanup. Include provider backup retention in your published privacy policy. Review the included Terms/Privacy with the actual operator before launch.

## Safe local import and recovery

1. Open **Account & cloud** from the library; sign in and verify email.
2. Review local project names, chapter/image counts and the destination account email. On a shared browser, do not select someone else's projects.
3. Check project selections and explicit ownership consent, then **Upload selected projects**.
4. The existing editable backup v3 packages originals, Raster/native sessions, Text & Bubbles, Composition & FX, presets and assets. Hash-addressed parts are individually verified before a revision becomes visible. No local image is replaced.
5. A separate IndexedDB transfer journal is scoped by account UUID + local project ID. Refresh and upload again to resume. Parts are deduplicated; no image copies are stored in the journal. A server compare-and-swap prevents overwriting a newer revision. If a project changed during upload, publishing stops. Explicit **separate copy** resolves a conflict without modifying the prior cloud head.
6. **Restore locally** downloads and verifies the manifest and every chunk before using the existing strict backup importer. Existing local project IDs are refused rather than overwritten. **Download package** offers a verified complete recovery package. Use a fresh browser/profile to inspect another revision safely. There is no automatic continuous synchronization or automatic merge of divergent graphics documents.
